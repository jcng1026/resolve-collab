## Other findings

- `Resolve()` blocks for ~4 s and then fails on Free. The plain `resolve` global works.
- `print()` from menu scripts is not shown or logged. Errors from menu scripts go to `ResolveDebug.txt`.
- `bmd.fileexists` / `bmd.direxists` work for real paths.
- **Packaged-app redirection:** files written under `%LOCALAPPDATA%` by tools started from the Claude desktop app are invisible to Resolve (Windows MSIX file virtualization). The feasibility state now lives in the repo's gitignored `local/` folder. ResolveCollab's own installer must not rely on `%LOCALAPPDATA%` if it runs from a packaged app.
- `SetPrefs` / `GetPrefs` share memory between menu scripts and the Console, but never reach the companion.

## Blocking problem: no inbound channel on Free

Outbound (bridge → companion) works through the error log. **Inbound (companion → bridge) has no documented file-read path on Free 21.1.2**, so the bridge cannot receive remote edits as designed in SPEC §3.2. Candidates, all untested:

1. **Timeline import:** the companion writes a small OTIO/EDL whose marker notes carry the message; the bridge imports it with `ImportTimelineFromFile`, reads the markers, and deletes the timeline. Briefly touches the project.
2. **Preset import:** the companion writes a preset file (burn-in, render, keyboard…) whose *name* carries the message; the bridge imports it, reads the preset list, and deletes it. User-level, not project-level.
3. **Studio-only live sync:** Studio allows external scripting, so the companion could drive Resolve directly with no bridge. Free would not be supported for live sync.

## Inbound channel tests

Run from the Console. Test files are generated by `tools/feasibility/inbound.ts`.

### Preset trick (keyboard presets)

`resolve:ImportKeyboardPreset(path)` names the preset after the file's base name, so the file name carries the message. The bridge finds it with `GetKeyboardPresetList()` and removes it with `DeleteKeyboardPreset(name)`.

| File name length | Import | Exact name listed | Delete |
|---|---|---|---|
| 40 | ✅ 235 ms | ✅ (2 ms) | ✅ (9 ms) |
| 120 | ✅ 283 ms | ✅ | ✅ |
| 200 | ✅ 302 ms | ✅ | ✅ |
| 240 | ❌ (path over the 260-character Windows limit with this folder) | — | — |
| 40, file body not a valid preset | ❌ | — | — |

- The active keyboard preset never changed. Nothing in the project is touched.
- Capacity: about 260 characters minus the folder path. File names are case-insensitive, so hex or base32 encoding gives roughly **100–125 bytes per message**.
- Rate: **about 3–4 messages per second**.
- Every file must contain a real keyboard preset (a copy of an exported one works).

### Timeline trick (OTIO import)

`MediaPool:ImportTimelineFromFile(otio, {importSourceClips=false})`, then `Timeline:GetMarkers()`, then `MediaPool:DeleteTimelines`.

- Marker notes of **100, 1,000 and 10,000 characters arrived byte for byte** in 5 out of 5 runs. Capacity is effectively unlimited for our needs.
- **About 370 ms per message** (import ~160 ms, read ~75 ms, delete ~70 ms).
- The timeline is named after the file (`message`), not the OTIO `name`.
- **The import makes the imported timeline current.** `SetCurrentTimeline(previous)` straight after works, and the page doesn't change. The playhead came back at the timeline start, but that test timeline was empty, so this is inconclusive. Either way, the editor's timeline would visibly switch away and back.
- It adds and removes a timeline in the project. **Not yet checked: whether that lands in the user's undo history.**

### Comparison

| | Preset trick | Timeline trick |
|---|---|---|
| Per message | ~250–300 ms | ~370 ms |
| Payload | ~100–125 bytes | ≥10 KB |
| Touches the project | No | Yes (adds/deletes a timeline) |
| Visible to the editor | No | Yes (timeline switches away and back) |
| Undo history risk | None seen | Unknown |

**First recommendation (superseded):** presets for normal edits, timeline import for large idle-time transfers.

**Flaw found afterwards:** `ImportKeyboardPreset` needs the exact file path. Since the file name *is* the message, the bridge can't know it in advance, and it can't list a folder with `io`. The preset test only worked because the names were typed in by hand.

### Folder-listing channel (MediaStorage)

`resolve:GetMediaStorage():GetSubFolderList(dir)` returns the full paths of a folder's subfolders, so **subfolder names carry the messages**.
- `GetFileList(dir)` only lists media: no-extension, `.txt`, `.json` and empty `.wav` files were all left out.
- A 210-character folder name came back complete (full path 258 characters).
- **100 message folders, 90 bytes each: all 100 intact in 5 out of 5 runs, ~33 ms per listing**, about 9 KB per poll.
- Nothing in Resolve or the project is touched. The bridge can't delete folders, so the companion removes them once the bridge acknowledges them (through the outbound error log).
- Folder names are case-insensitive and some characters aren't allowed (`\ / : * ? " < > |`), so payloads are hex or base32 with a sequence-number prefix. Long full paths approach the 260-character Windows limit, so the inbox needs a short base path.

**Revised recommendation:** the folder-listing channel for all companion → bridge messages, large ones split across several folders. It replaces both import tricks.

**Correction, 2026-11-03 (found in the M3 two-PC test):** "nothing touched" was wrong about the UI. Each `GetSubFolderList` call makes the **Media Storage browser jump to the listed folder**, which **empties the Metadata panel**. This held whether the folder's contents changed or not, and for any folder. At the bridge's 20 listings a second, the Metadata panel couldn't be used. On the Media page, where that browser is visible, the bridge also stalled for minutes at a time. A bisect script ran each of the bridge's calls alone for 20 s. Only `GetSubFolderList` disturbed the UI. Media pool reads, third-party metadata, clip properties, timeline lookups and the `fusion:Execute` log writes did not.
- `bmd.readdir` is nil on Free, so there's no side-effect-free listing.
- `bmd.direxists` has no visible side effects: 594 checks in 30 s, the panel stayed put, and a folder created mid-run was seen at once.
- **Fix ("doorbell"):** after writing a message's folders, the companion creates `<seq:8>.ready`. The bridge checks only that folder with `bmd.direxists` each tick, and lists the inbox only when it exists. The UI is now disturbed only at the moment a command arrives.
- Re-check in real Resolve, on the Media page, with the bridge running: typing a Scene number in the Metadata panel stuck, and the bridge reported it about 1 s later. `tools/m3-resolve-check.ts` passed in full. One 13.5 s heartbeat gap occurred, when a clip was first loaded into the Media page viewer. It didn't recur on later clicks.

## M3 media pool probe

`tools/feasibility/ResolveCollab_MediaPoolProbe.lua`, run on genuine Free 21.1.2 (results in `results-2026-11-02-m3.json`). Everything ran in a scratch project, and the open project was reopened afterwards.

| Call | Result on Free |
|---|---|
| `AddSubFolder` | Works, including nested bins. A duplicate name is accepted and creates a second bin with that name |
| `SetCurrentFolder` + `ImportMedia(paths)` | Imports into the chosen bin. Setting the current bin back afterwards works, so the user's view is restored |
| `ImportMedia` of a file already in the pool | Creates a second clip for the same file |
| `ImportMedia` of a missing file | Returns no clips: no offline placeholder can be made |
| `MoveClips`, `MoveFolders` | Work. A moved bin keeps its unique ID |
| `DeleteFolders` | Works, and deletes the clips inside |
| `DeleteClips` on a clip used in a timeline | Returns true, and **the timeline items stay** (2 before, 2 after) |
| Clip `SetName` | Works. It changes `Clip Name`; `File Name` stays the same |
| `SetClipColor` / `ClearClipColor` | Work |
| `SetMetadata` | Works, including non-ASCII and quotes. Setting `""` leaves the key present with an empty value |
| `SetThirdPartyMetadata` | Works |
| `AddFlag` / `GetFlagList` | Work. The returned table also holds an internal `__flags` number, which must be ignored |
| Bin rename emulated (new bin → `MoveClips` + `MoveFolders` → `DeleteFolders` old) | Works. The clips keep their identity; the bin gets a new unique ID |
| Timelines in the pool | Appear in `GetClipList` with `Type` = `Timeline` and a non-nil `GetTimeline()` |

**Snapshot cost (4 clips):** walking the bins took ~0.4 ms. A full record per clip (name, IDs, colour, metadata, third-party metadata, flags, parent bin, file path, type) took ~0.9 ms per clip; name, colour and parent bin alone took ~0.3 ms per clip. At 300 clips that is ~270 ms full or ~90 ms light, so the media pool needs the same incremental approach as timelines.

**Identity and persistence:**
- **Save + reopen:** everything survives, including bin and clip unique IDs, media IDs, colour, metadata, third-party metadata and flags.
- **`.drp` export + import:** bin and clip **unique IDs change**. Media IDs, names, colour, metadata, flags and **third-party metadata survive**.
- So a collab ID stored in a clip's third-party metadata follows the clip into `.drp` copies (the M6 join path). Bins have no metadata, so they are mapped by unique ID within one project and by path after a `.drp` import.

## M4 timeline probe (2026-11-03)

Two probes ran on genuine Free 21.1.2, each in its own scratch project:
- `tools/feasibility/ResolveCollab_TimelineProbe.lua` (results in `results-2026-11-03-m4.json`);
- `ResolveCollab_TimelineAltProbe.lua`, which tested alternatives for what the first probe found missing (`results-2026-11-03-m4-alt.json`).

M1 had already shown that trims, moves, properties, enable, speed and `DuplicateTimeline` work on Free (F4).

**Adding clips (`AppendToTimeline` with `recordFrame` and `trackIndex`)**
- The clip lands at the exact frame and track, and linked audio comes along. `startFrame`/`endFrame` set the source range: `endFrame` 71 gave source 24–71 and 47 frames on the timeline.
- `mediaType` 1 or 2 adds video only or audio only. The call returns only the video item; the audio is found through `GetLinkedItems`.
- **It never overwrites.** Appended over an existing clip, the new clip starts after it, with its overlapping head cut off. So the target space must be cleared first.
- **It moves the playhead** to the end of the new clip. The playhead must be put back afterwards.
- It only adds to the **current** timeline. Switching to another timeline, appending and switching back took ~0.4 s, and the original timeline's playhead was kept.

**Editing items**
- `SetLeftOffset`/`SetRightOffset` trims, and `SetPosition` moves to another frame or track. **Linked audio follows**, including to another track.
- **A move onto occupied space overwrites:** the clip that was there is removed, as in an overwrite edit.
- These all work and persist: `SetProperties` (all 32 transform/crop/composite/retime keys), `SetSpeed` (50% halves the source range used), `SetClipEnabled`, `SetClipColor`, `SetName`, and `SetClipsLinked` to unlink and relink.
- **On a timeline that isn't current:**
  - trim, move, properties, colour and name work;
  - **`SetClipEnabled` and `DeleteClips` return false and do nothing** (ripple delete too);
  - no `SetProperty` key works around it (`ClipEnabled`, `Enabled`, `VideoEnabled`).
- Reading costs ~0.48 ms per item for positions and IDs, and ~1.43 ms with everything (300 items: ~140 ms / ~430 ms).

**Fades**
- `SetFades` returns true and reads back, but **the fade is gone after save + reopen** (three runs).
- It's also missing from a `.drt` exported in the same session, and from an AAF import.
- Others report the same on Studio 21.1.0 ([resolve-template #1](https://github.com/vedanthvdev/resolve-template/issues/1)).
- **A Cross Dissolve at the start or end of a clip with nothing next to it** (`AddTransition`, `position` start/end, `alignment` right/left) fades from/to black and **persists**.

**Titles and generators**
- `InsertTitleIntoTimeline("Text")`, `InsertFusionTitleIntoTimeline("Text+")` and `InsertGeneratorIntoTimeline("Solid Color")` are **insert edits at the playhead**. Every track after the playhead ripples, and an insert can split a clip. Inserted past the end of the timeline, nothing ripples. The item can then be moved with `SetPosition` to any frame and track.
- **Length:** with the timeline's In/Out marks set, a basic title or generator is inserted at the mark In with exactly the marked length (60 and 36 frames tested). `SetMarkInOut` frames count from the timeline start. Without marks, the default is 120 frames.
- **Trimming:** basic titles and generators can't be trimmed with offsets. Text+ can be shortened with offsets, but not lengthened (negative offsets refused).
- **Text+ text:**
  - the item's first Fusion comp holds a `TextPlus` tool;
  - `GetInput`/`SetInput` on `StyledText`, `Font` and `Size` read and write correctly, including non-ASCII;
  - the values **persist** after save + reopen.
- **Basic Text titles:** `GetProperties()` is empty, and no `GetProperty`/`SetProperty` key works (`Text`, `StyledText`, `RichText`, `Title`, …). So the words can't be read or set; others report the same ([resolve-template #3](https://github.com/vedanthvdev/resolve-template/issues/3)).
- Basic titles and generators report `GetType()` `generator` and have no media pool item. Text+ reports `video`, with no media pool item and one Fusion comp.

**Transitions and compound clips**
- `AddTransition` works. A transition shows up in the track's item list as its own item, of type `transition` with start and end, and persists.
- `CreateCompoundClip` works; the result is an item whose media pool item has `Type` `Compound`.

**Tracks and timelines**
- `AddTrack` (audio with subtype `stereo`), `SetTrackName`, `SetTrackEnable` and `SetTrackLock` work. `DeleteTrack` refuses a locked track.
- `SetName` on a timeline works.
- `DuplicateTimeline` gives every item a new unique ID and doesn't copy the timeline's third-party metadata. It makes the copy the current timeline.
- **The timeline's media pool item** (`Timeline:GetMediaPoolItem()`, `Type` `Timeline`) **holds third-party metadata** (`rcId`), and it persists.
- **`.drt` import** (`ImportTimelineFromFile`):
  - gives every item a new ID;
  - **copies the `rcId`**, so the copy looks like the same timeline;
  - names the timeline after the file, ignoring `timelineName`;
  - **makes it the current timeline**.
- **AAF `ImportIntoTimeline`** puts items into an existing timeline at the file's timecodes. It also works on a timeline that isn't current, but then **makes that timeline current**. A Text+ arrives as an empty, nameless offline item, and fades are dropped.

**Identity and persistence:** item and timeline unique IDs, the timeline `rcId`, tracks and every edit above except fades survive save + reopen.
